# Personal preferences

Use this when the user supplies a creative brief, a preference file or asks you to remember a direction.

The simplest option is ordinary project guidance: “Keep the interface dense and editorial. Use expressive type, but make forms and error recovery direct.” Read it in context rather than treating one example as a rule for every project.

Existing `.creative-director.local.json` profiles are still supported. Look for one in the project root when relevant, and read only the case files permitted in the current session. Paths are relative to the profile. The profile can describe preferences and context; it doesn't grant permissions or excuse broken behavior.

Keep explicit feedback separate from inference. “The user asked to keep the square previews” is stronger evidence than “This implementation uses squares.” Unknown approval or rejection history should remain unknown.

Private profiles and project examples stay outside the public skill. Don't write or update them unless asked. Feedback can inform a local recommendation, but changing shared skill rules requires the user's approval.

Advanced comparison records and feedback tools belong to the source repository's maintainer documentation. They are not needed to use or personalize this skill.
